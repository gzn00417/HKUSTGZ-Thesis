## 3. Executive judgment

The integrated revision does not redesign the deck. It combines a conservative thesis-level restructuring, committee-review correction, and evidence-boundary calibration.

The external review material was useful, but not every suggestion warranted a slide change. The remaining high-risk issues were narrower:

1. inconsistent use of “14 models” where the thesis means 14 evaluated baselines;
2. Study 2 wording that conflated input-token reduction with generic efficiency or latency gains;
3. Study 2 backup conclusions that overstated universality, budget-wise dominance, or a single root cause;
4. Study 3 wording that implied an unreported latency threshold or formal metric guarantee;
5. an SCL notation/sign ambiguity in the thesis text;
6. a backup data-scaling interpretation that incorrectly treated temporal ability as one of the six plotted UVRB abilities;
7. efficiency plots described as operating curves even though each method is represented by one reported configuration.

The revision therefore changes claims and interpretation rather than visual structure. It uses 48 visible text edits, 16 targeted speaker-note edits, and one table-cell correction.

## 4. Principles used in the final evidence-boundary pass

### 4.1 What was changed

- Correct factual or terminology errors.
- Replace unsupported guarantees with empirical observations.
- Distinguish reported results, plausible mechanisms, and limitations.
- Preserve interpretable numbers that help a committee evaluate the evidence.
- Make the main argument readable without relying entirely on oral explanation.
- Keep generalizability as a cross-study thread while avoiding one global, unsupported definition.

### 4.2 What was deliberately not changed

- No main slide was added, removed, or reordered.
- No thesis figure was redrawn, cropped, or semantically edited.

- The 100-instance audit was not converted into a visible Wilson confidence interval. Such an interval would be a derived statistic, not a thesis-reported result.

## 8. The unresolved SCL notation issue and conservative resolution

The thesis defines retrieval as maximizing learned relevance `δ`. The SCL section then correlates `δ` positively with a quantity named Euclidean distance, even though smaller Euclidean distance normally indicates greater proximity. No implementation code was available in the adjacent paper repository to determine whether the implementation uses negative distance, similarity, or another transformed reference.

The deck therefore does not assert a sign-sensitive equation beyond the paper’s covariance mechanism. It uses:

- `δ`: learned relevance;
- `g`: a geometric reference derived from embedding distance;
- `ρ(δ,g)`: the soft ordering-alignment statistic.

This is intentionally conservative. It does not alter the thesis and does not claim a formal metric guarantee. If the implementation later confirms `g = -||h_u-h_v||₂`, a future revision may state that definition explicitly.

## 9. Rebuild instructions

From the repository root, use Python 3 with `python-pptx` installed and Node.js with `@oai/artifact-tool` importable either from the local package environment or through `NODE_PATH`:

```bash
python3 slides/v0.5-build/build-v0.5.py \
  --source slides/thesis-slides-v0.4.pptx \
  --output /tmp/thesis-slides-v0.5-rebuild.pptx
```

If `@oai/artifact-tool` is not installed in the active Node.js environment, set `NODE_PATH` to the appropriate `node_modules` directory before running the same command. No user-specific absolute dependency path is stored in the repository documentation.

The builder intentionally refuses to overwrite an existing output. For validation, use a temporary output path as above. The delivered final artifact is `thesis-slides-v0.5.pptx`.

`v0.5-build/build-v0.5.py` is the only public command needed. It first reconstructs the original v0.5 restructuring from v0.4, then runs the committee-review and evidence-boundary stages stored in the same directory. The JavaScript stages use exact-match guards, while all intermediate decks remain in a temporary directory and are removed automatically.

### Repository cleanup and future-version reference (2026-07-18)

The final deck content was not changed during this cleanup. The purpose was to reduce root-level build clutter without discarding the reproducible intermediate logic:

1. `v0.5-build/build-v0.5.py` is the single stable command for maintainers. No v0.5 build script remains in the `slides/` root.
2. The former root-level files `build-v0.5.py`, `build-v0.5-base.py`, `build-v0.5-stage1.mjs`, and `build-v0.5-stage2.mjs` were retained and organized under `v0.5-build/` according to their actual responsibilities.
3. The base stage reconstructs the 79-slide narrative and layout from the unchanged v0.4 deck.
4. The committee-review stage performs guarded ordering, terminology, claim-strength, and notes corrections.
5. The evidence-calibration stage performs the final thesis/appendix evidence-boundary corrections and exports the requested output.
6. The two intermediate PPTX files exist only inside a system temporary directory during a build. A successful build removes them automatically. A failed build also leaves no repository artifact because the temporary-directory context handles cleanup.

For a later version, preserve this separation of concerns even if the implementation is reorganized: start from a named immutable source deck, keep narrative restructuring distinct from evidence calibration, use exact-match or equivalent drift guards, refuse in-place overwrite, build intermediates outside the repository, and record both accepted and rejected review suggestions. This prevents a future revision from silently losing the reasoning accumulated in v0.5.
